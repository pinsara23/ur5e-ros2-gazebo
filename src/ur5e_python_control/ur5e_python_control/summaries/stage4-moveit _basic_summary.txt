# Stage 4 — MoveIt 2 Motion Planning with UR5e

## Stage 4 Goal

The goal of Stage 4 was to move from manually commanding the UR5e controller to using **MoveIt 2 for motion planning**.

Before Stage 4, our architecture was mainly:

```text
Python program
    ↓
FollowJointTrajectory action
    ↓
scaled_joint_trajectory_controller
    ↓
ros2_control
    ↓
UR5e in Gazebo
```

We manually created joint positions, waypoints, and timing.

In Stage 4 we changed the architecture to:

```text
Python program
    ↓
MoveItPy
    ↓
MoveIt 2
    ↓
OMPL motion planner
    ↓
RobotTrajectory
    ↓
Trajectory Execution Manager
    ↓
scaled_joint_trajectory_controller
    ↓
ros2_control
    ↓
UR5e in Gazebo
```

---

# 4.1 MoveIt 2 Concepts

We learned that MoveIt 2 is a motion-planning framework for ROS 2.

MoveIt does not directly replace `ros2_control`.

Instead:

```text
MoveIt decides HOW the robot should move.

ros2_control performs the actual joint motion.
```

Main concepts learned:

* Robot Model
* Robot State
* Planning Group
* Planning Scene
* Motion Planning
* Planning Pipeline
* OMPL
* Collision Checking
* RobotTrajectory
* Trajectory Execution Manager
* Controller selection
* Planning vs Execution

---

# 4.2 Direct Controller vs MoveIt

Previously, in Stage 2:

```text
We chose:
- joint positions
- waypoints
- trajectory timing
```

```python
point.positions = [
```

We manually told the robot how to move.

With MoveIt:

```text

- trajectory
```

# 4.9 Creating the MoveItPy Configuration

The UR MoveIt package contains:

```text
/opt/ros/jazzy/share/ur_moveit_config
```

Its config files include:

```text
config/
    chomp_planning.yaml
    joint_limits.yaml
    kinematics.yaml
    moveit_controllers.yaml
    ompl_planning.yaml
    pilz_cartesian_limits.yaml
```

The SRDF files are:

```text
srdf/
    ur_macro.srdf.xacro
    ur.srdf.xacro
```

Our Python configuration became:

```python
from pathlib import Path

from moveit_configs_utils import MoveItConfigsBuilder
from moveit.planning import MoveItPy

moveit_config = (
    MoveItConfigsBuilder(
        robot_name="ur",
        package_name="ur_moveit_config"
    )
    .robot_description_semantic(
        Path("srdf") / "ur.srdf.xacro",
        {"name": "ur5e"}
    )
    .planning_pipelines(
        pipelines=["ompl"],
        default_planning_pipeline="ompl"
    )
    .to_moveit_configs()
)

config_dict = moveit_config.to_dict()

config_dict["planning_pipelines"] = {
    "pipeline_names": ["ompl"]
}

config_dict["use_sim_time"] = True
```

Then we created MoveItPy:

```python
moveit = MoveItPy(
    node_name="moveit_state_test",
    config_dict=config_dict
)
```

---

# 4.10 Why `use_sim_time=True` Was Required

At first MoveItPy reported:

```text
Didn't receive robot state with recent timestamp
```

Gazebo was using simulation time while the Python node was using normal system time.

We fixed it with:

```python
config_dict["use_sim_time"] = True
```

After that, MoveIt could correctly receive `/joint_states`.

# 4.15 Creating a Separate Goal RobotState

We must not do:

```python

```

because that makes both variables point to the same object.

We used:

```python
import copy

goal_state = copy.copy(current_state)
```

```python

    "ur_manipulator",
    goal_positions
)
```

And gave it to MoveIt:

```python
ur5e.set_goal_state(
    robot_state=goal_state
)
```

# 4.16 Configuring the Planner

We imported:

```python
from moveit.planning import (
    MoveItPy,
    PlanRequestParameters
)
```

The Jazzy API required two arguments:

```python
plan_parameters = PlanRequestParameters(
    moveit,
    "plan_request_params"
)
```

Then configured:

```python
plan_parameters.planning_pipeline = "ompl"

plan_parameters.planner_id = \
    "RRTConnectkConfigDefault"

plan_parameters.planning_time = 5.0

plan_parameters.planning_attempts = 1

plan_parameters.max_velocity_scaling_factor = 0.5

plan_parameters.max_acceleration_scaling_factor = 0.5
```

Important distinction:

```text
planning_pipeline = "ompl"
```

selects the OMPL planning system.

While:

```text
planner_id = "RRTConnectkConfigDefault"
```

selects RRTConnect inside OMPL.

Conceptually:

```text
MoveIt
   ↓
OMPL
   ↓
RRTConnect
```

# 4.21 Path vs Trajectory

We learned an important distinction.

A path describes:

```text
Where should the robot pass?
```

A trajectory describes:

```text
Where should the robot pass
+
when should it reach those states?
```

Conceptually:

```text
Geometric path
     ↓
Time parameterization
     ↓
Trajectory
```

The MoveIt log showed:

```text
Calling Planner 'OMPL'
```

then:

```text
Calling PlanningResponseAdapter
'AddTimeOptimalParameterization'
```

and:

```text
ValidateSolution
```

# 4.24 Trajectory Start-State Validation

# 4.28 Adding a Collision Object

Imports:

```python
from moveit_msgs.msg import CollisionObject
from shape_msgs.msg import SolidPrimitive
from geometry_msgs.msg import Pose
```

Created the object:

```python
collision_object = CollisionObject()

collision_object.header.frame_id = "base_link"
collision_object.id = "test_box"
```

Created box geometry:

```python
box = SolidPrimitive()

box.type = SolidPrimitive.BOX

box.dimensions = [
    0.20,
    0.20,
    0.20
]
```

Created its pose:

```python
box_pose = Pose()

box_pose.position.x = 0.50
box_pose.position.y = 0.50
box_pose.position.z = 0.50

box_pose.orientation.w = 1.0
```

Connected geometry and pose:

```python
collision_object.primitives.append(box)

collision_object.primitive_poses.append(
    box_pose
)

collision_object.operation = CollisionObject.ADD
```

Added it to MoveIt:

```python
with planning_scene_monitor.read_write() as scene:

    scene.apply_collision_object(
        collision_object
    )

    scene.current_state.update()
```

Output:

```text
Collision object added!
```

# 4.29 Meaning of `base_link`

This:

```python
collision_object.header.frame_id = "base_link"
```

means that the object's X, Y, and Z coordinates are interpreted relative to the UR5e base coordinate frame.

Example:

```python
x = 0.5
y = 0.5
z = 0.5
```

means:

```text
0.5 m in X
0.5 m in Y
0.5 m in Z
```

relative to `base_link`.

# 4.35 Why MoveIt Is More Powerful Than Direct Joint Control

Direct controller approach:

```text
Python
 ↓
JointTrajectory
 ↓
controller
 ↓
robot
```

The controller mainly knows:

```text
Move these joints according to this trajectory.
```

It does not independently understand a box, wall, table, or shelf.

MoveIt adds:

```text
Robot model
+
Planning scene
+
collision checking
+
motion planner
+
trajectory generation
```

So the complete architecture becomes:

```text
High-level goal
      ↓
MoveIt
      ↓
Robot model
+
Planning scene
      ↓
OMPL
      ↓
Collision-free trajectory
      ↓
Trajectory Execution Manager
      ↓
ros2_control controller
      ↓
robot
```
